# AeroSight MSUP 参赛演示与项目报告设计

状态：演示设计稿，不代表下述全部链路已经真实验收。默认图文报告 8–12 页、视频 5 分钟；以比赛最终要求调整。当前优先 P0 历史素材真实分析，暂停追查司空 OpenAPI 媒体阻塞，不安排真实飞行。

## 1. 作品定位与故事

作品名称建议：AeroSight 时空智能巡检平台——设备、数据、算法与智能体的协同框架。

一句话：AeroSight 是覆盖设备接入、时空数据、算法服务、智能体、任务编排与业务处置的统一平台；本次以人车巡查的完整闭环，展示这些模块如何协作。

统一表达：平台是主体，巡查案例是验证载体。先介绍整体能力版图，再沿一个案例深入，最后回到可复用与扩展价值。“完整框架”指模块组织与协作设计，不等于每一种设备、算法、自动飞行模式均已实测完成。详细报告大纲见 report-outline.md，视频与配音提纲见 video-outline.md。

主场景：公园周边人车巡查。业务人员每天面对一批航拍图，需要快速找到人车目标、判断哪些值得现场核查、形成工单并保存证据。演示用真实历史可见光照片；场景标题随实际样本调整，不能先写好违规结论再找图配合。

最小闭环：已导入历史图像 → 手动或定时触发 Task → 冻结本次素材范围 → 本地 YOLO 检测 → 真实模型依据证据研判 → 人工复核 → Issue → 报告及证据回溯。

“时空”体现：地图上的采集位置、原始拍摄时间、本次处理时间、来源任务与工单时间线。照片采集位置不能冒充目标精确坐标；同一张图反复处理不能称为多时相变化检测。多期比较作为后续增强。

## 3. 样本与本地 YOLO 方案

### 样本先行

从已授权司空历史可见光 JPEG 中选择 6–12 张，其中尽量包含：

- A：至少一张人/车清晰可见的图片，用来展示真实检测和人工确认核查线索。
- B：至少一张没有目标或无需生成线索的图片，展示有限范围的零检测/不建案结果。
- C：至少一张小目标、遮挡或上下文不足的图片，展示 needs_review；不得强迫模型输出预写答案。

先人工登记目标和可见性，再运行模型，记录误报、漏报、阈值和耗时。如果现有高空照片对通用模型太难，选择其中目标更清晰的样本，或使用明确标注来源的补充授权图片；不把补充样本伪装成司空采集。红外图暂不交给普通 RGB 预训练模型。

视频先用于开场素材背景。第一版实际检测输入是图片；视频抽帧作为可选第二阶段，需要保存原视频、帧时间和对应资产，不能声称已支持连续视频跟踪。

### 服务方案

- 首选 Ultralytics YOLO11n 预训练模型；模型包/权重固定版本并记录摘要。macOS arm64 优先尝试 PyTorch MPS，不支持时用 CPU；真实耗时测完再写报告。
- 首批只启用 person、car、bus、truck、motorcycle、bicycle；不宣称支持火灾、垃圾、违建或违规行为直接判定。
- 高分辨率航拍先试整图推理；若目标太小，再加重叠切片、原图坐标还原和跨切片 NMS。是否增加切片由样本实测决定。
- FastAPI 包装为现有 synchronous http-json Provider；接收平台 runId、inputAsset.accessUrl、checksum 和 parameters，返回类别、置信度、原图像素框和模型版本。
- 平台已有输入协议 aerosight.algorithm.input/v1。检测框用 type=bbox、x/y/width/height，与原图像素系一致；不得返回缩放图或切片局部坐标。
- 请求图片必须核验大小、类型、解码和摘要，失败返回失败，空检测返回成功空集合。runId/资产摘要/参数/权重版本用于重试缓存，避免重复计算。
- 模型不需要外部商业识别 Key；模型首次安装和下载完成后可本地推理。现有真实大模型 Provider 仍需联网，不能宣传全离线。

### 本地通信必须解决

当前 Provider 校验要求 HTTPS，拒绝 localhost/回环及受限网络；算法输入图片地址也要求 HTTPS。不能直接填写 http://localhost:8000 假定能跑。

实现前选择并验证一种明确的演示部署方式：优先独立演示环境的受信 HTTPS 入口与固定本地服务目标，或为本地部署新增仅运维配置可用的固定 Provider 适配。若采用开发例外，必须限制到指定目标，保留签名图片/摘要校验，不能全局关掉出站检查。确认 Go 服务能访问 YOLO，YOLO 也能访问资产签名地址。具体接入方式作为实现任务单独决策，不在本设计稿中声称已经实现。

## 4. 智能体与业务语义

输入：本次观察范围、检测框/类别/置信度、图像来源时间、业务巡查说明、可用位置证据。

输出：摘要、引用的检测证据、建议动作，以及 create/no_issue/needs_review 等现有契约允许的决定。没有禁行规则或现场背景时，检测到车辆只能形成“车辆目标待核查”建议，不能认定违停；看到人员不能直接认定闯入。

演示主线允许真实模型返回 needs_review，随后由用户确认“是否需要现场核查”并建案。复核是产品价值的一部分，不是为让演示成功改写检测结果。不要把所有检测框机械地变成案件，也不要人为固定模型结论。

一次 Task 关联全部证据；再运行同一来源，验证不重复创建相同案件。若现有防重规则与实际样本不一致，应修复并测试，不能在录屏前手动清空案件掩盖。

## 5. 五分钟演示分镜

| 时间 | 页面/画面 | 操作与旁白重点 | 要证明什么 |
| --- | --- | --- | --- |
| 00:00–00:20 | 航拍照片 + 一句话流程图 | “巡检难点不止拍到，而是把数据转成可追踪的处置。”字幕：历史航拍素材真实分析 | 业务问题与演示范围 |
| 00:20–00:45 | 项目总览/地图/来源资产 | 打开采集点或原图，展示拍摄时间和来源；设备卡片快速带过 | 空间、时间和数据来源 |
| 00:45–01:05 | 算法与智能体配置 | YOLO 人车检测、本地模型版本；智能体负责证据研判 | 能力可替换，分工清楚 |
| 01:05–01:45 | Task 编辑页 | 从已有图片模板创建/打开，展示五步 YAML；切换参数表单；解释定时是触发器 | 可编排任务，不是固定功能按钮 |
| 01:45–02:25 | 发布版本与 Run 详情 | 手动触发同一份任务，观察 observe→detect→assess 的真实状态；等待部分可加速并标明 | 后台流程真实执行 |
| 02:25–03:05 | 原图/检测证据 | 展示真实 YOLO 框、类别、置信度、模型版本和分析图片范围 | 可核验识别结果 |
| 03:05–03:45 | 智能体研判与复核 | 展示证据引用和理由，确认一条现场核查线索；短暂展示另一条不建案/待复核结果 | 模型判断与人工闭环 |
| 03:45–04:20 | Issue 详情 | 从研判进入工单，查看原图、任务关联；演示指派和处置反馈 | 结果能落实到工作 |
| 04:20–04:45 | Run 报告 | 展示范围、检测/线索统计、案件和证据回链；返回原始资产 | 全流程可追溯 |
| 04:45–05:00 | 结果总览/触发配置 | 展示已验证的定时分析记录（若已完成），总结平台分工和下一步真实飞行接入 | 自动化能力与清晰边界 |

手动运行是主录屏方案。另录一段实际 schedule 触发同类 assets 任务的连续证据，停用后保留 Run 的 schedule 来源。若时长不足，视频中展示配置及真实记录；未产生真实定时记录时只介绍配置，不把手动 Run 说成定时触发。定时分析固定素材不等于自动发现最新照片。

完整无人机自动飞行链路仅在架构图用虚线标注“后续接入”；不播放模拟画面并声称真实起飞。本轮不得启动真实飞行或新建远端飞行计划。

## 7. 截图与录制清单

统一 16:9、建议 1920×1080；使用同一个演示项目、Task 和 Run，截图中名称/编号/统计要一致。产品截图必须来自实际页面，不用设计稿替代完成状态。

截图编号：01 项目地图；02 原图与元数据；03 算法版本；04 Task YAML；05 参数表单与触发器；06 Run 步骤；07 检测框；08 研判证据；09 人工复核；10 Issue 反馈；11 报告；12 定时 Run 记录（可选）。避免录入 Key、签名 URL 和个人信息；应用截图可裁剪到有效区域。

录制分为一条连续主流程与若干细节补镜。原始录像保留，剪辑只压缩等待、不调整前后因果或替换统计。准备一条真实完成 Run 供网络波动时回放，并明确说“查看刚才的运行结果”。截图从最终验收 Run 统一采集，避免报告与视频不同步。

## 8. 演示前执行任务（优先顺序）

1. **D1 样本包**：取得 6–12 张授权 RGB 原图，标注实际可见目标与时间来源；正式导入演示项目，确认地图/元数据/原图可打开。
2. **D2 本地检测服务**：部署固定版本 YOLO + FastAPI，解决受限的本地服务通信；先单图，再批量，记录耗时、类别、误报漏报。不通过就先调整样本/切片，不往后做假结果。
3. **D3 Provider 接线**：注册算法版本与映射，用平台签名资产调用真实模型；验证空结果、单图失败、超时和原图坐标还原。
4. **D4 主线打通**：正式 Task 从 assets 到 YOLO、真实 AI、人工复核、Issue 和报告；补当前步骤衔接和页面缺口。
5. **D5 三种结果验收**：至少一个需要核查并确认建案的样本、一个不建案样本、一个需复核样本；保存真实证据，不强制 AI 对预定图输出特定决定。
6. **D6 自动化与处置**：验证一次 schedule 触发、同源重跑不重复建案，以及 Issue 反馈操作；演示项目与实机控制隔离。
7. **D7 演示整理**：统一中文名称和导航；突出主任务状态、来源时间、检测框和证据；排练一次并记录实际时间。
8. **D8 材料交付**：基于通过的 Run 采集截图，撰写 8–12 页报告，录制/剪辑 5 分钟视频及保留完整原片。

门槛：D1–D4 通过才安排正式截图；D5–D6 通过才写效果与可靠性结论。优先完成主线，复杂航线规划、实机飞行、视频追踪、多时相变化检测和完整拖拽编辑器不进入这次演示关键路径。

本任务表是参赛演示交付清单，不自动修改既有 OpenSpec 32 项的验收范围与完成状态。后续实现应回填相关真实验收证据，原完整飞行目标仍单列未完成。


比赛要求核对见 competition-requirements.md。五分钟视频为制作基线，不是已确认的初赛时长限制；创业组决赛 10＋3 分钟，高校组 5＋2 分钟。正文初稿见 project-report-draft.md，旁白初稿见 narration-draft.md，截图登记见 evidence-register.csv。
