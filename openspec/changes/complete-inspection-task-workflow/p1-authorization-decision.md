# P1 预检与定时授权补充方案（待确认）

状态：设计建议，尚未替换 design/spec/tasks 中的正式要求，尚未实施授权数据写入。确认本方案仅授权软件实现及隔离模拟测试，不授权真实飞行。

## 已核实的缺口

- `httpapi/mission_control.go` 已有 approve 分支，向既有审批请求插入人工决定；数据库触发器执行人数、有效期和申请人与批准人分离约束。
- FlightHub 动作入口与 worker 要求 Run 的安全策略、预检 allowed 和有效授权；目前正常成功测试的前置通过 SQL fixture 构造，不能用作产品创建路径。
- 当前审批绑定单个 task_run，无法表达“人工批准某个已发布版本在限定窗口内按计划重复运行”。不能由调度器伪造审批人或批量写 approved 请求补齐。

## 建议行为

1. **单次手动运行**：创建业务 Run 后，由正式服务生成预检快照及 pending 审批请求，页面显示设备、航线冻结版本、安全策略与提示。复用已有人工确认流程；批准后仍须通过提交前复查。
2. **定时运行**：增加显式“计划执行授权”。用户选择已发布 Task 版本、唯一连接器/设备、冻结航线、安全策略版本、有效起止时间和最多执行次数，发起授权申请。具有 `mission:approve` 权限的用户按现有审批人数与分离规则确认。
3. **按计划执行**：调度器只消费已批准且未撤销的计划授权。每次 occurrence 创建自己的业务 Run，重新验证委托者权限、授权范围、有效期、剩余次数、航线版本、设备状态和远端预检。授权不能跨 Task 版本、设备或航线复用。
4. **授权留痕**：每个 Run 记录所使用的计划授权和一次性消费记录。该记录明确是计划授权的执行凭证，不伪装成人工逐 Run 批准，也不向 approvals 表插入虚构的人类决定。
5. **单一调度归属**：AeroSight 是唯一 schedulerOwner，远端只提交 immediate。停用 Task 或撤销授权阻止后续提交；修改发布版本、航线或策略需重新申请，不能自动扩大授权。
6. **不确定结果**：提交超时/未知 ACK 保留本次授权消费和设备占用，进入待对账状态；不退款并重飞。明确尚未提交的预检失败按失败记录，不自动补执行错过的 occurrence。
7. **业务暂停/取消**：停止后续业务推进并显示远端可能仍在飞行；不把业务取消解释为飞机已停止。实机控制继续是独立、明确授权动作。

## 最小实现范围

- 补预检服务：生成服务端事实快照，保留采集时间、策略版本、检查结果；blocking error 拒绝进入可提交状态。快照过期或关键范围改变必须重新检查。
- 补单次审批申请 API，复用现有审批决定和审计规则。
- 增加计划授权及消费记录，外键固定项目/团队/版本范围；唯一键保护同一 occurrence 幂等，事务锁保证执行次数不能并发超额。
- 补计划授权的申请、确认、撤销、查看接口及 Task 页面入口。
- 扩展动作授权校验以明确区分“单次人工批准”和“有效计划授权消费”，保留旧单次路径；不会用伪造的单次 approved 请求迁就旧查询。
- 将 observe 接入既有 flight_action ledger、业务 Run 绑定、告警暂存和媒体等待，再复用 P0 后半段。保留一次派发与未知结果对账约束。

## 必须验证的案例

- 未批准、已过期、已撤销、次数耗尽、申请人与批准人分离或权限不满足时，无远端提交。
- 同一 occurrence 被多个实例扫描、服务重启、重复请求时，仅有一条消费记录及最多一次提交意图。
- 发布新版本、设备/航线/策略变动时拒绝沿用旧授权；不能用动态 inputs 越过被冻结范围。
- 授权在预检后撤销，提交前再次检查并拒绝；已经开始的远端提交不声称可通过数据库事务撤回。
- 未知 ACK 不自动重飞，已有消费记录保留；迟到飞行结果不推进已取消业务 Run。
- 通过正式 API 创建授权及人工决定，经隔离协议替身串联 cron、预检、一次 immediate、媒体及 P0 后半段；不以 SQL 人工设置成功状态作为验收。

## 本次待确认的产品选择

建议采用“手动逐次审批 + 定时按上述有限计划授权”的组合，以保留真正定时无人值守触发能力。若改为每次定时触发后都等待人工批准，则不能把它当成相同的产品行为，需要同步修改原始定时目标的验收说明。
